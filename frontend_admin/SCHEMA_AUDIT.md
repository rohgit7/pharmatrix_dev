# Frontend/backend schema audit

**Scope:** existing admin frontend routes and every API contract they call. Backend model and Pydantic schemas are authoritative; request payloads, response types, UI fields, nullable display, defaults, and enum choices were cross-checked. This checklist does not create screens for backend workflows that have no existing admin UI.

**Validation:** `npm run build` passes. The focused backend vehicle/driver test set passes (34 tests). Decimal response serialization was checked with the project’s FastAPI/Pydantic stack: `Decimal` values are JSON strings, so response types below use `DecimalString`; request form values remain numeric.

## Existing frontend surfaces

- [x] **Login / current user** — `POST /api/auth/login`: required `email`, `password`; response `access_token`, `refresh_token`, `token_type`, `user_id`. `/api/auth/me` user fields: `id`, `auth_user_id`, `name`, nullable `email`, `role` (`ADMIN | DRIVER | CUSTOMER | FACILITY`), `is_active`. UI sends credentials and consumes token/user response without inventing fields.
- [x] **Overview** — dashboard response: `total_pickups`, `pending_pickups`, `today_scheduled_pickups`, `active_routes`, `pending_warehouse_intakes`, `open_exceptions` (integers), `total_collected_weight_kg` (number). Health responses: `{status, service}` and `{database}`.
- [x] **Pickups** — filters use `PickupStatus` (`REQUESTED | SCHEDULED | ASSIGNED | IN_PROGRESS | COLLECTED | FAILED | CANCELLED`). Schedule request: required `scheduled_date` (datetime). Cancel request: required `reason`, 1–1000 characters; UI now captures it. List/detail response: `id`, `public_id`, `pickup_code`, `customer_id`, `location_id`, `status`, `priority` (`NORMAL | HIGH | URGENT`), nullable `requested_date`, `scheduled_date`, `notes`, `failure_reason`, `collected_at`, plus `created_at`, `updated_at`. Nullable dates/notes render safely.
- [x] **Routes / stops / proof** — route create: required `warehouse_id`, `route_date`, non-empty `pickup_ids`; optimize request: `warehouse_id`, `route_date`. Route response: `id`, `route_code`, `route_date`, `warehouse_id`, nullable `driver_id`, `vehicle_id`, `planned_distance_km`, `planned_duration_seconds`, `optimized_at`, `status`, `created_at`, `updated_at`, `stops`. Stop response: `id`, `sequence_number`, `stop_type` (`PICKUP | WAREHOUSE`), nullable `pickup_id`, `warehouse_id`, `arrival_time`, `departure_time`. Optimization response includes route date/warehouse, available vehicles, created routes, assigned pickups, and per-route IDs, pickup IDs, distance, duration, and load. Proof lookup validates a positive integer stop ID and displays `stop_id`, `proof_uploaded`, `signed_url`, and API-provided `expires_in`.
- [x] **Warehouses** — create requires `code` (1–50), `name` (1–150), `address` (1–500), `city`/`state` (1–100 each), `postal_code` (1–20), `latitude`, and `longitude`; there are no coordinate defaults. Warehouse service bounds latitude to `[-90, 90]` and longitude to `[-180, 180]`. Update allows those same fields plus `active`; each is optional/nullable per `WarehouseUpdate`. Response includes all create fields, `id`, `active`, `created_at`, `updated_at`. Latitude/longitude inputs map to create/update payloads.
- [x] **Warehouse intake** — receive request: positive `received_weight_kg` up to 100000, optional nullable `discrepancy_reason` and `notes` (each max 1000). Classify request: non-empty `items`; each requires `bin_color`, `waste_type`, positive expected/received weights up to 100000, optional nullable `notes` (max 1000). Waste colors: `YELLOW | RED | WHITE | BLUE | BROWN`; waste types: `HUMAN_ANATOMICAL | ANIMAL_ANATOMICAL | SOILED | EXPIRED_DISCARDED_MEDICINE | CHEMICAL | CHEMICAL_LIQUID | CONTAMINATED_RECYCLABLE | SHARPS | GLASSWARE | METALLIC_IMPLANT | HAZARDOUS_OTHER`. Intake response includes `id`, `intake_code`, route/warehouse/driver/vehicle IDs, `status`, expected and nullable received weights, nullable received time/discrepancy/notes, timestamps, and items. Item response includes IDs, classification, weights, nullable notes, and creation time.
- [x] **Facilities** — create requires existing `user_id` belonging to a FACILITY user; `facility_code` (1–50), `legal_name` (1–200), `phone` (1–20), `email` (1–255), `license_number` (1–100), address (1–500), city/state (1–100), postal code (1–20), latitude, longitude. `license_expiry` is optional/nullable. Update fields are optional and may be nullable as defined by the backend; `active` is optional. Response includes all these fields, `id`, `active`, and timestamps. No speculative facility fields or coordinate defaults remain.
- [x] **Disposal shipments** — create request requires `intake_id`, `facility_id`, `items[]` (`warehouse_intake_item_id`, positive `expected_weight_kg`); `notes` is nullable/optional. UI supports multiple items and sends each one. Response includes `id`, `public_id`, `shipment_code`, intake/facility IDs, status, expected and nullable received weights, nullable dispatch/receive timestamps, discrepancy and notes, and items (ID, intake item ID, expected/nullable received weight, nullable notes). Backend `Decimal` response weights use `DecimalString`; request weights remain numeric. Dispatch is an action with no request body.
- [x] **Fleet** — driver onboarding requires valid `email`, `name` (1–150), `employee_id` (1–50), `phone` (1–20), `license_number` (1–100); nullable `license_expiry` is optional. Onboard response: `driver_id`, `user_id`, `auth_user_id`, `message`. Driver list response: `id`, `user_id`, employee ID, phone, license number, nullable expiry, status (`ACTIVE | INACTIVE | SUSPENDED`), `is_available`, timestamps. Vehicle create requires registration number (1–50) and vehicle type (`BIKE | THREE_WHEELER | VAN | TRUCK`); positive `capacity_kg` (max 10 digits/2 decimal places) is optional/nullable. If omitted, backend resolves `logistics.default_vehicle_capacity_kg`; the UI leaves it blank and omits it rather than inventing a value. Vehicle response includes ID, registration, type, Decimal-string capacity, status (`AVAILABLE | ASSIGNED | MAINTENANCE | INACTIVE`), timestamps; nonexistent `active` is not used.
- [x] **Invoices / payments** — invoice response fields: `id`, `public_id`, `invoice_number`, customer ID/public ID, pickup ID, pricing plan/version IDs, currency, subtotal, tax, total, amount paid, outstanding amount, status, issued date, nullable due/paid dates, pricing snapshot, nullable notes, timestamps, and line items. Line-item response: `id`, invoice ID, item type, description, quantity, unit price, amount, metadata JSON, creation time. All backend `Decimal` values are typed as JSON decimal strings and parsed only for display/comparison; currency-aware display uses invoice currency. Payment create requires UUID `invoice_id`, positive amount (max 12 digits/2 decimals), `payment_method` (`CASH | UPI | BANK_TRANSFER | CARD | OTHER`); `payment_reference` is nullable/optional (max 100), notes nullable/optional (max 2000). Payment response includes ID, UUID invoice ID, Decimal-string amount, method, status, nullable reference/idempotency key/notes, paid and created times.
- [x] **Customer documents** — response includes `id`, `customer_id`, document type (`AADHAAR | DRUG_LICENSE | BUSINESS_REGISTRATION | GST_CERTIFICATE | OTHER`), nullable `document_number`, `is_verified`, `created_at`. Verification action maps the `verified` query parameter; download uses the separate signed download URL response. The backend deliberately omits `document_url` from list responses, so the frontend does not invent or expect it.
- [x] **Operational exceptions / proof** — filters use backend status (`OPEN | ESCALATED | RESOLVED`) and exception type (`PICKUP_FAILED | WAREHOUSE_INTAKE_DISCREPANCY | DISPOSAL_SHIPMENT_DISCREPANCY`). Response includes ID, type/status, source type/ID, reason, opened time, nullable escalated/resolved times, nullable resolver ID and resolution notes. Resolve request requires `resolution_notes` (1–2000 characters); UI captures it and enforces max length.
- [x] **Configuration / approvals / audit** — list response: `id`, `key`, nullable description, data type (`STRING | INTEGER | DECIMAL | BOOLEAN | JSON`), scope, nullable scope ID/current version ID, active flag, timestamps. Detail adds nullable `current_version`; history returns configuration and versions. Version response includes ID/configuration ID/version, JSON value, status, nullable effective dates, creator, nullable approver/reason/reference/previous version/rollback version, creation time, nullable approval time. Change create: configuration ID; JSON proposed value (backend defaults null); risk level (defaults `HIGH`, max 20); required reason (1–2000); nullable reference (max 150); nullable effective time. Review comment is nullable (max 2000). Rollback requires target version ID and reason (1–2000), with nullable reference (max 150) and effective time. Change response includes all backend fields: IDs, nullable base/rollback IDs, proposed JSON value, status, risk, reason, nullable reference/effective time, creator, nullable approver/rejector/review comment, timestamps. Audit response includes IDs, nullable version/change IDs, actor, action, JSON old/new values, nullable reason/reference, timestamp. Pending status uses `PENDING_APPROVAL`; list responses do not claim a `current_version`.
- [x] **WhatsApp templates** — create requires notification type, template key and Meta template name (each 1–100); language defaults to `en_US` (2–20), parameter keys default empty, active defaults true. Update fields are optional/nullable with matching string lengths. Notification types include all backend options: `PICKUP_REQUESTED | PICKUP_SCHEDULED | PICKUP_REMINDER | DRIVER_ASSIGNED | PICKUP_COMPLETED | SHIPMENT_DISPATCHED | SHIPMENT_RECEIVED | DISPOSAL_COMPLETED | EXCEPTION_ESCALATED`. Response includes ID, notification type, key/name/language, parameter keys, active flag, timestamps.
- [x] **Topbar notifications** — response includes ID, notification type, channel (`IN_APP | WHATSAPP | EMAIL`), status (`PENDING | PROCESSING | SENT | FAILED`), title/body, nullable JSON metadata, nullable read/sent times, created time, nullable provider status/time. Read action returns the same response shape.
- [x] **Settings** — currently uses health/database health endpoints only; no backend entity form or persisted settings payload is represented.

## Backend models without a corresponding current admin form/page

These were identified so their absence is explicit; no new UI was invented because the request requires preserving the existing architecture. Backend-only workflows remain unrepresented in this admin frontend:

- [ ] Customer onboarding and profiles: `Customer`, `CustomerLocation`, `PharmacyProfile`, `DistributorProfile`, `HospitalProfile`, `ClinicProfile`.
- [ ] Customer/facility waste workflows: the customer-disposal response workflow (not a SQLAlchemy model), `DisposalCertificate`, certificate download/issue flow, shipment receipt/reconciliation actions beyond the current shipment-create/dispatch UI.
- [ ] Driver operations: `DriverVehicleAssignment`, driver route/stop execution, pickup verification and related proof upload workflows.
- [ ] Pricing: `PricingPlan`, `PricingPlanVersion`, `CustomerPricingAssignment`.
- [ ] Backend operational/audit records not exposed as current admin CRUD pages: `AuditLog`, `Event`, `RazorpayOrder`, and `RazorpayWebhookEvent`.

## Audit result

- [x] Existing frontend form, filter, request, response, nullable/default, enum, and relevant display contracts listed above are aligned to backend schemas.
- [x] No database migration or database model change was introduced.
- [x] `VehicleCreate.capacity_kg` remains optional in the API because the backend applies the configured default; the frontend preserves that behavior.
- [x] Focused backend tests: 34 passed across vehicle API, vehicle service integration, and driver/vehicle assignment integration.
